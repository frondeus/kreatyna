Context

The recipes discovery (brief, mockups) decided that the app's first home is the Mac (D-02), as one Mac-native app with the catalog and recipes side by side (D-03). A small Mac catalog epic comes before recipes (D-04): the catalog gets full create, edit and delete on the Mac (D-28), and Counter leaves the app (D-17).

Today there is only the iOS app in ios/Kreatyna/Kreatyna.xcodeproj (from the ingredient catalog epic). The Rust core, SQLite store and ingredient widgets already exist and are tested; this epic adds a Mac window over them, moves Counter to krucyfiks's examples, and removes it from the app.

Goal: launching the Mac app shows the ingredient catalog in a native three-column window, where you can browse, search, create, edit and delete ingredients, with data kept in Rust's SQLite store. The iOS app keeps working.

Architecture

Repository and Xcode

  • The ios/ folder becomes apple/ (MAC-09), since it will hold both apps.
  • The Xcode project is generated by XcodeGen from a readable apple/Kreatyna/project.yml (MAC-10, E-15). Every Xcode change, including the new Mac target (MAC-00), is a small YAML diff that agents write and you review as text. You don't need to touch Xcode at all.
  • A separate macOS app target (KreatynaMac) with its own Swift Testing and XCTest UI targets.
  • The generated UniFFI bindings and the small Swift adapter over the Rust runtime (today's AppModel, logging, database location) are shared by both targets: project.yml lists one shared source folder in both. Views are not shared: Mac views are Mac-native (split view, toolbar, context menus), iOS views stay as they are.
  • The Rust library is built for macOS next to the existing ios-build-* devenv scripts. The Mac app is sandboxed, so Swift passes Rust a database path in the app's container.

Rust

  • No new domain. The ingredient list, detail and form widgets and the store are reused.
  • Rust sends a stack of views; Swift only lays it out. Every render already carries the whole stack: the list view is always there, and on top of it come the open layers, such as Garlic's detail, or Garlic's detail with the edit form above it (IngredientCatalogView: list plus screen). On iOS, Swift shows the layers as pushed screens. On the Mac, it shows them side by side: the list in one column, the top layer (detail, form, or “Select an ingredient”) in the detail column. Because the list is part of every render, renaming Garlic in the form updates its row in the list as soon as Rust saves it. Swift keeps no navigation state; clicking a row only sends an event, and the next render shows the result.
  • Start with the stack; the Mac will grow into “islands”. MAC-04 starts with today's stack. The Mac differs from iOS (the list stays clickable while a form is open), and later multi-window work will want independent panes, each with its own widget. When a Mac rule differs, a Mac-specific coordinator composes the same list, detail and form widgets with its own navigation rules (E-14). Not everything has to be unified across platforms; how islands work is discovery for later epics. Either way, Rust makes the decisions.
  • Counter moves to an examples/ folder in the krucyfiks repository (MAC-11), where it keeps showing how background effects work. Then it leaves this app (MAC-03), together with the tab concept and the counter table. The app is just the catalog until the recipes epic introduces Rust-owned sidebar sections (REC-01).

Testing

  • Per build-swift-presentation: Swift Testing for the adapter and wiring, controlled macOS snapshots (fixed window size, light and dark) for the Mac views, a few real-core XCTest UI flows. Rust tests stay the place for rules.
  • Each slice ships demo screenshots of the running Mac window. MAC-02 turns the run-and-capture steps into a skill.

Suggested order

    Slices

    Each slice is its own jj change and review. Its implementation plan is written in tasks/<ID>.md when the slice starts, not before. Layers show where the slice changes code: db migration and Diesel, rust domain and widgets, ffi UniFFI types and build, swift SwiftUI and its tests.

    Open questions

    None. Every question raised during planning and review is recorded as a decision above (Q-M1 → E-10, Q-M2 → E-12, Q-M4 → E-14, Q-M5 → E-13, Q-M6 → E-11; Q-M3 was folded into E-08).

    Out of scope

    • Recipes: the next epic, Recipe MVP.
    • Sidebar sections as a Rust concept: they arrive with the first second section (REC-01).
    • Custom menus and keyboard shortcuts beyond what SwiftUI gives for free; text zoom (D-43) comes with recipes or later.
    • Multiple windows, App Store signing, notarisation, sync between devices (D-02 “later”).
